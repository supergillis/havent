# Containerless Camera Streaming

Investigation + design options for exposing the Avent camera to Home Assistant **without shipping our own
Docker container**, while keeping (a) a real `camera.*` entity and (b) a plain URL a tablet can open
without Home Assistant.

Status: **option A built and verified against a real SCD953 on 2026-08-09.** Facts below were
verified against `homeassistant==2026.8.1` (unpacked wheel), `AlexxIT/go2rtc@v1.9.14` (the version
HA bundles) and the camera itself — not from memory. The code is in
`custom_components/philips_avent/{signaling,stream_server,sdp}.py` and `player.html`, behind the
`stream_backend` option; the throwaway prototype it grew out of has been deleted. A first field
trial (2026-08-09) exposed a session-pool exhaustion failure mode and refuted one conclusion
previously recorded here; see "First field trial" and
`docs/superpowers/plans/2026-08-09-builtin-backend-session-hygiene.md`.

## Problem

Today video needs three moving parts: the integration writes `philips_avent_bridge_<entry>.json`, the
add-on container supervises `avent-webrtc-bridge addon --config …`, and the camera entity points at
`rtsp://<host>:38554/<name>`. That container costs us:

- three add-on cards (`aventproxy-bridge-addon{,-beta,-dev}`) that must be kept in lockstep, plus a
  multi-arch image build on every release;
- a version-skew failure mode that is entirely ours (bridge older than integration → missing config
  fields → "No access");
- HA Container / Core users can't use the add-on store at all;
- ~5 000 lines of Go we own.

The media path itself is already fine: signaling over Tuya's cloud MQTT, then H.264/SRTP **peer to
peer over the LAN** (the camera advertises a host candidate — `WHITEPAPER.md:909`). Nothing about
"direct to Tuya with STUN" is missing; what we are actually paying for is *terminating* that WebRTC
session somewhere and republishing it.

## What actually has to happen

Four jobs. Every option below is a different assignment of these four to different processes.

| # | Job | Today | Already in Python? |
|---|-----|-------|--------------------|
| 1 | Tuya cloud API: `p2p.main.pre.link.get`, `rtc.session.init`, `rtc.config.get`, `user.info.get` | Go `pkg/tuya/mobile_api.go` | **Yes, mostly** — `api.py` has the signer and `get_rtc_config()` (`api.py:250`) |
| 2 | MQTT signaling: derive creds, connect TLS 8883, publish `offer`/`candidate`/`resolution`/`disconnect`, read `answer`/`candidate` | Go `pkg/tuya/mqtt.go`, `mqttCamera.go` | No — but payloads are **plain JSON, no encryption** (`mqttCamera.go:186`), and the cred derivation is three MD5s (`mobile_api.go:253-278`) |
| 3 | WebRTC termination: DTLS-SRTP, RTP depacketize, (HEVC: fmp4 over datachannel) | Go, pion | No |
| 4 | Republish: RTSP server, snapshots, fan-out to N viewers | Go `pkg/rtsp/*` (~2 100 lines) | No |

Jobs 1 and 2 are cheap in Python. Jobs 3 and 4 are the expensive ones — and **Home Assistant already
ships a process that does both**: go2rtc.

## Verified constraints (this is the load-bearing part)

**HA bundles go2rtc and manages it itself** — `homeassistant/components/go2rtc/server.py`:

- config is generated by HA, users cannot edit it;
- `app: modules: [api, exec, ffmpeg, http, mjpeg, onvif, rtmp, rtsp, srtp, webrtc, ws]`.
  `webrtc` **is** enabled. `tuya` is **not**. Neither are `mp4`/`hls`;
- `exec: allow_paths: [ffmpeg]` → we **cannot** have HA's go2rtc exec our binary;
- `rtsp: listen: "127.0.0.1:18554"` → go2rtc's RTSP is loopback-only, useless for a tablet;
- HTTP API is a **unix socket**; TCP `:11984` only when the user sets `go2rtc: debug_ui: true`
  (+ `username`/`password`), which also enables the UI at `/`;
- `webrtc: listen: ":18555/tcp"`, `ice_servers: []` (cleared);
- managed go2rtc only exists when `is_docker_env()` — HA Core in a venv has none unless the user
  installs go2rtc themselves and sets `go2rtc: url:`.

**HA's go2rtc provider accepts any scheme go2rtc supports** — `go2rtc/__init__.py`:

```python
def async_is_supported(self, stream_source: str) -> bool:
    return stream_source.partition(":")[0] in self._supported_schemes  # from GET /api/schemes
```

It then does `streams.add(identifier, [stream_source, "ffmpeg:<id>#audio=opus…"])` by itself. So a
camera entity whose `stream_source()` returns `webrtc:ws://…` is registered in HA's go2rtc with **no
extra plumbing from us**.

**Snapshots can come from go2rtc** — `camera/__init__.py:235`: `_async_get_stream_image()` asks
`webrtc_provider.async_get_image()` first (go2rtc `/api/frame.jpeg`), but only when the entity sets
`use_stream_for_stills = True` (`camera/__init__.py:484`). No ffmpeg-on-RTSP needed.

**go2rtc's `webrtc:` source protocol is trivial** — `internal/webrtc/client.go:70-180`. For a
`ws://` URL with no `#format` it speaks its own protocol:

1. offers `video recvonly`, `audio recvonly`, `audio sendonly` (three m-lines — see risk R1);
2. sends `{"type":"webrtc/offer","value":"<sdp>"}`;
3. **the very next message must be** `{"type":"webrtc/answer","value":"<sdp>"}`;
4. then `{"type":"webrtc/candidate","value":"candidate:…"}` in both directions.

No auth, no ICE-server negotiation (`go2rtcClient(rawURL)` ignores the query string entirely).

**go2rtc already speaks Tuya** — `pkg/tuya/{client,mqtt,smart_api,cloud_api,interface}.go`, added in
v1.9.13. Same skill parsing, same streamType/HEVC logic, same MQTT camera frames as our bridge. It
exposes a clean `TuyaAPI` interface (`interface.go:9-23`) with two implementations: the
`ismartlife.me` web portal and the IoT-platform Cloud API. **Neither can authenticate an Avent
account** — that is exactly the gap our `mobile_api.go` fills. Adding a third implementation is a
~300-line file plus ~15 lines in `Dial()`.

## Options

### A. Signaling shim in Python + HA's bundled go2rtc as the media engine ⭐ (proven)

We keep jobs 1+2 (Python, easy), hand jobs 3+4 to go2rtc, which HA already runs.

```
camera.stream_source() -> "webrtc:ws://127.0.0.1:38555/avent/<cam_id>?t=<secret>"
                                            │
HA go2rtc provider ── streams.add() ──▶ go2rtc ──ws──▶ aiohttp endpoint inside the integration
                                            │              │ tuya API calls (api.py)
                                            │              │ tuya MQTT signaling (new mqtt.py)
                                            └── SRTP/H.264 ◀┘ ...offer/answer relayed
                                                 direct from the camera over the LAN
```

The shim owns: one Tuya session per camera, SDP rewriting (audio-first reorder, strip `a=extmap`,
reshape m-lines), candidate buffering (nothing may precede the answer), `SendResolution(0)` after
connect, and session teardown — which, as the spike found, must **not** be tied to the websocket
closing (R8).

- **No container, no binary, works on today's HA.** Deletes the Go tree and all three add-on cards.
- Camera entity: WebRTC in the dashboard via the go2rtc provider; snapshots via `/api/frame.jpeg`
  with `use_stream_for_stills = True`.
- Two-way audio is *easier* than today: go2rtc's offer already carries an `audio sendonly` m-line.
- Loses HLS / `camera.record` / Chromecast (go2rtc's RTSP is loopback-only and `stream_source` is no
  longer an RTSP URL). For a baby monitor that is a fair trade; if it isn't, see Phase 3.
- HA Core-in-venv users need their own go2rtc (`go2rtc: url:`) — document it.
- Cost: ~700–900 lines of Python (MQTT client, signaling session, ws endpoint, SDP rewriter).
  The prototype in `tools/webrtc-shim/` is **530 lines** and already streams.

### B. Upstream a mobile-SDK auth mode into go2rtc's `tuya://` source ⭐ (endgame)

Port `mobile_api.go` to a third `TuyaAPI` implementation upstream, then
`stream_source()` returns `tuya://a1.tuyaeu.com?device_id=…&sid=…&app_key=…`. Everything native:
two-way audio, HEVC datachannel, snapshots, RTSP, and go2rtc's own UI.

Blocked on **two** upstream PRs: go2rtc (`pkg/tuya/mobile_api.go` + `Dial`) *and* HA core (add
`"tuya"` to `_APP_MODULES` in `go2rtc/server.py`, since HA's module allowlist would otherwise keep
the source disabled). Then wait for an HA release that bumps the bundled binary. Months, and outside
our control — so it is the destination, not the next step. Note our repo would still be the place
where the Avent signing key lives; the go2rtc side only needs the credentials passed in the URL.

### C. Integration-spawned static binary (no Docker)

Keep the Go bridge, drop the container: download the per-arch static binary from our GH release into
the config dir and supervise it from `async_setup_entry` — exactly what HA does for go2rtc.

- Smallest delta, keeps every current behavior (talkback, HEVC, `rtsp://ha:38554/<name>` for VLC).
- But: we still build and ship binaries (only the Docker layer disappears), the maintenance win is
  small, and downloading + `chmod +x` + exec'ing a binary from a HACS integration is a grey zone
  users and reviewers will (reasonably) push back on.
- Good as an escape hatch if A's SDP negotiation turns out to be untenable.

### D. Native WebRTC camera entity (no go2rtc at all)

Implement `Camera.async_handle_async_webrtc_offer()` and relay the *browser's* offer to the camera.
Media never touches HA. Lowest latency, least CPU.

- No snapshots, no HLS, no recording — HA advertises only `StreamType.WEB_RTC` when a camera is
  natively WebRTC (`camera/__init__.py:810-820`).
- Every viewer opens its own camera session (Tuya's concurrent-session limit is unknown).
- Doesn't answer the "URL without HA" requirement on its own.
- Not a primary option, but the *same* shim code from A can serve this — see Phase 2.

### E. Full Python port (aiortc + Python RTSP/HLS server)

Reimplement jobs 3+4 in Python. ~2 000 lines, heavy deps (`av`, `pylibsrtp`), and re-solves problems
go2rtc already solved. Only if both A and B die.

|  | container | binary | HA entity | HLS/record | tablet URL | new code |
|--|-----------|--------|-----------|------------|-----------|----------|
| A | none | none | WebRTC + snapshot | ✗ | via shim page / go2rtc debug UI | ~800 py |
| B | none | none | full | ✓ | go2rtc debug UI | ~350 go, 2 upstream PRs |
| C | none | ours | full | ✓ | `rtsp://ha:38554/x` | ~150 py |
| D | none | none | WebRTC only | ✗ | with a player page | ~600 py |
| E | none | none | full | ✓ | ours | ~2 000 py |

## The tablet URL

Requirement: open a URL on a tablet, no Home Assistant in the path. Three answers, best first:

1. **Serve our own player page next to the shim** (Phase 2). The integration already listens on its
   own port for go2rtc; add `GET /avent/<cam>` returning a ~60-line HTML page whose JS does
   `RTCPeerConnection` against the same signaling endpoint. Media goes **browser ↔ camera directly**
   over the LAN; HA relays nothing. Plain `http://<ha-ip>:38555/avent/nursery`, no auth prompt, no
   HA frontend, sub-second latency. Because we own the JS we can also munge the offer client-side
   (drop `extmap`, keep H.264 + PCMU), which sidesteps risk R1 for this path entirely.
2. **go2rtc debug UI**: `go2rtc: {debug_ui: true, username: …, password: …}` in `configuration.yaml`
   → `http://<ha-ip>:11984/stream.html?src=philips_avent_<unique_id>&mode=webrtc`. Zero code from
   us. Note MSE/HLS won't be offered (HA doesn't enable go2rtc's `mp4`/`hls` modules), WebRTC and
   MJPEG will.
3. **User-run go2rtc** (`go2rtc: url: http://…`) for anyone who wants RTSP/HLS/whatever on the LAN.
   Still a container, but a generic one someone else maintains.

Option C's answer is simply `rtsp://<ha-ip>:38554/<name>` — fine for VLC, useless in a browser.

## Spike results (2026-08-09)

Phase 0 ran against the live camera. All three spikes passed; the prototype lives in
`tools/webrtc-shim/` and its README carries the protocol details.

- **Signaling in Python works and is fast.** Cloud API + MQTT connect + subscribe worked first try
  reusing `api.py`'s signer; the camera answers an offer in **~0.12 s** and trickles host, srflx and
  TURN-relay candidates within ~150 ms.
- **Media works.** `go2rtc` 1.9.14 (same version HA bundles) consumed
  `webrtc:ws://127.0.0.1:38555/avent/<camera_id>` and served it as RTSP: 12 s recorded as
  **H.264 1280×720 + PCMU audio**. No Go binary, no container anywhere in the path.
- **This camera is H.264 only** — skill reports 1920×1080 (streamType 2) and 1280×720 (streamType 4),
  both `codecType 2`, audio L16/16000 mono. The HEVC datachannel path is not reachable here.
- **R1 was real, and worse than expected — but cheap to fix.** The camera does not merely dislike
  go2rtc's three m-lines; given a **video-first** offer it answers with an *empty* video section
  (`m=video … 96` immediately followed by the audio m-line, no mid/ice/rtpmap, missing CRLF). The Go
  bridge has always offered audio first, which is why it never saw this. Reordering to audio-first in
  the shim produces a complete, correct answer.
- **Two more findings the shim has to handle** (both in the prototype):
  - a rejected (port 0) m-line must still carry the offer's `rtpmap`/`fmtp` lines, or go2rtc fails
    with `payload type not found`;
  - **go2rtc closes the signaling websocket as soon as ICE connects** (`internal/webrtc/client.go`,
    `defer conn.Close()`). Tying the Tuya session's lifetime to that socket kills the stream ~0.4 s
    after it starts. Session lifetime must instead end on the camera's `disconnect` frame, on
    replacement by a new session, or on an idle guard. **This is the one piece of the design that is
    still unsatisfying** — see R8.
- **WHEP looks easier than the ws protocol** and is worth re-evaluating for the shipping code:
  go2rtc's `whepClient` offers only **two** m-lines (video recvonly, audio recvonly) and a
  fully-gathered offer, so no third-m-line surgery and no candidate relaying — at the cost of having
  to inline the camera's trickled candidates into the answer before responding.

## Recommendation

**A now, B in parallel, C in the back pocket.**

- **Phase 0 — spikes. Done, all passed** (see above).
- **Phase 1 — the shim. Done.** See "What shipped" below.
- **Phase 2 — the player page. Done.**
- **Phase 3 — flip the default**, mark the add-on cards deprecated, then delete
  `avent-webrtc-bridge/` + the three cards + the image build from `release.yml`. Keep the Go tree in
  git history and keep `WHITEPAPER.md` as the protocol reference. Blocked on the field trial and on
  the measurement in R8.
- **Phase B (parallel, opportunistic):** upstream the mobile-SDK `TuyaAPI` implementation. If it
  lands *and* HA enables the module, Phase 1's shim becomes a fallback for old HA versions and the
  integration's `stream_source()` collapses to one `tuya://` string.

## What shipped

| File | Lines | Owns |
|------|-------|------|
| `sdp.py` | ~200 | Offer/answer rewriting. No imports at all; 27 unit tests against captured SDPs. |
| `signaling.py` | ~290 | Tuya cloud handshake and the MQTT frames. One broker connection per account. |
| `stream_server.py` | ~270 | The aiohttp site: go2rtc's websocket protocol and session lifetime. |
| glue | ~100 | `camera.py` branch, options flow, diagnostics, setup/teardown. |

One consumer, one negotiation path. The camera entity's `stream_source()` returns
`webrtc:ws://127.0.0.1:38555/avent/<camera_id>?t=<token>`, which HA's go2rtc provider registers
as-is.

**A browser player page was built and then removed** (2026-08-09, at the user's request). It served
the "watch on a tablet without HA" requirement by having the browser negotiate straight with the
camera — verified to the point of RTP flowing to a browser-shaped client, though its JavaScript
never ran in a real browser. Dropping it removed ~220 lines, the LAN bind, a second HTTP surface and
the only unverified code in the feature, and it collapsed the session registry from
`(camera, consumer)` to `camera`, which made "a new dial replaces the previous session" exactly
right rather than a heuristic. The requirement is now met by go2rtc's own UI (`debug_ui: true`),
which costs no code at all. It is in git history if a second consumer ever justifies it.

**Session lifetime — the answer to R8, twice corrected.** After the answer is relayed we hold
nothing the camera needs; a session lingers 120 s (long enough to hear a `disconnect` from a stream
that dies at birth), then we drop our own state. But "the camera reclaims its own slot promptly" —
the claim the previous version of this paragraph rested on — was wrong, and so was a
first-field-trial conclusion that the `disconnect` frame is peer-scoped and must never be sent. The
verified mechanism (2026-08-09, against go2rtc source, the trial logs and Tuya's TuyaOS IPC
firmware docs): the frame is *session-scoped* — ids are per session, cameras send per-session
disconnects, and both go2rtc's `pkg/tuya` and this repo's Go bridge send it for their own session
id at their own teardown. The observation behind the peer-scoped conclusion was a misread (the
"surviving" session had merely been replaced by the next 10 s snapshot poll) and contaminated (a
second go2rtc was dialling the same endpoint). The shipped rules: send `disconnect` — own session
only, the API cannot express another — on answer timeout, handshake failure and
replacement-by-redial; stay silent when the camera hung up first and wherever media may still be
flowing (linger expiry, config entry unload, server stop). See
`docs/superpowers/plans/2026-08-09-builtin-backend-session-hygiene.md`.

**`keep_stream_running` (2026-08-09, default off)** makes the built-in backend behave like the
bridge it replaced: one long-lived Tuya session, held whether or not anyone is watching, in
exchange for instant opens and zero session churn. Two findings shaped it, both verified against
`homeassistant==2026.8.x` source:

* **Home Assistant's own `preload_stream` camera preference is the wrong lever.** Its
  `EVENT_HOMEASSISTANT_STARTED` listener (`camera/__init__.py`) calls
  `camera.async_create_stream()`, `stream.add_provider("hls")` and `stream.start()` — an
  ffmpeg/HLS pipeline fed from `stream_source()`, which for this backend is a `webrtc:ws://…` URL
  ffmpeg cannot open. Setting the pref would make the recurring "Error opening stream (Protocol
  not found)" permanent, and it means writing another integration's user preference from ours.
  What actually keeps the producer dialled is go2rtc's **own** preload API (`PUT /api/preload`),
  the same one HA's go2rtc provider drives — reached through the `Go2RtcConfig(url, session)` HA
  parks at `hass.data["go2rtc"]` and `go2rtc_client.Go2RtcRestClient(...).preload`.
* **Preload can only be armed for a stream go2rtc has registered**, which happens on the first
  dial. So the option is driven from the one place success is observed: `CameraSource.on_answered`,
  a plain callback fired by `stream_server._negotiate` after the camera answers (the module stays
  HA-free; `preload.py` supplies the callback). Every answer re-arms it, because a dial only
  happens when the producer is down — exactly when the preload has stopped doing its job. That
  matters because HA's go2rtc provider turns preload *off* whenever the camera entity unregisters
  (i.e. on every options reload) and on any camera-preferences update. Setup therefore also
  re-enables preload for streams go2rtc still knows (`StreamPreloader.async_resume`, scheduled
  after the platform forward so it cannot race the entity's provider registration), which makes
  the option survive reloads; after a full HA restart go2rtc starts empty, and the stream goes hot
  again at the first view or dashboard thumbnail. With the option off (or the add-on backend
  selected), setup best-effort disables any preload a previous configuration armed. Everything
  degrades quietly when go2rtc is absent or errors: one warning per entry, never a failed setup.

**Two regressions against the Go bridge were caught in review before shipping**, both real:

* *Per-session MQTT clients.* Tuya's client id is derived from the account and the phone device id
  with nothing per-session in it, so two connections knock each other off the broker. The Go bridge
  shares one client per device (`mqtt_manager.go`); the first draft of `signaling.py` did not. Now
  one `SignalingHub` per account multiplexes every camera and every session by session id. This is
  also why the add-on and the built-in backend must not run on one account at once — the setup code
  deletes the add-on's config file and says so in the log.
* *`stream_type`.* An early draft sent 0/1 based on a comment in go2rtc's Tuya source. The
  field-tested Go bridge sends the skill's own `streamType` (2/4 here) for H.264 and reserves 0/1
  for HEVC. This camera ignores the field either way, but other models may not, so parity won.

### First field trial (2026-08-09): the session pool

The first day of real use saturated the camera so badly the vendor app could not connect. The
mechanism, each link verified:

* **HA's thumbnail poll was the churn.** With `use_stream_for_stills = True` every still goes to
  go2rtc's `/api/frame.jpeg`, whose handler (`internal/mjpeg/mjpeg.go`) dials the producer, waits
  for one keyframe, then **stops the producer** — it does not share a running stream. Redial
  timestamps in the log were phase-locked to a 10.00 s period: an idle dashboard opened ~360
  complete Tuya sessions per hour. Fixed by a 60 s TTL frame cache behind
  `use_stream_for_stills = False` (`frame_cache.py`).
* **The pool is 3–5 sessions** (`max_client_num`, the range Tuya's [TuyaOS IPC firmware
  docs](https://developer.tuya.com/en/docs/iot-device-dev/tuyaos-package-ipc-device?id=Kcn1px33iptn2)
  recommend — vendor documentation, not a measurement on this unit). When full, the camera forcibly
  closes the *newcomer* — the vendor app's "Device Busy". Sessions abandoned mid-handshake become
  zombies reclaimed on firmware timers documented at ~20 minutes
  (`tuya_ipc_p2p_set_zombie_session_timeout`). Observed here: once the churn stopped, recovery took
  roughly ten minutes of retrying, with the vendor app locked out the whole time. This answers R5's
  ceiling and R8's "how long to reclaim a slot" measurement.
* **Answer latency is bimodal:** 74–135 ms when the camera answers at all; otherwise silence.
  `ANSWER_TIMEOUT` dropped from 20 s to 6 s, valid only alongside the cooldown: after an unanswered
  offer the server refuses to dial for 25 s — no cloud call, no offer — so the pool can drain
  instead of absorbing go2rtc's retries and its `ffmpeg:` second source's double-dial.

### Verified on hardware

* go2rtc 1.9.14 pulling `webrtc:ws://` through the real modules: 1280×720 H.264 frame out of
  go2rtc's RTSP.
* The player endpoint: HTTP 200 in 0.89 s, three m-lines matching the offer, audio clamped from the
  camera's `sendrecv` to `sendonly`, four camera candidates inlined plus `a=end-of-candidates`.
* A browser-shaped client (aiortc, two recvonly transceivers, gathered offer, one POST): ICE
  connected, 3 645 video and 778 audio RTP packets in 15 s. aiortc decoded the audio but not the
  video — it does not request a keyframe, which every browser does automatically, and go2rtc decodes
  the identical stream. This covered the player page, since removed.
* In Home Assistant itself (2026.7.1, official image under rootless podman, host networking): the
  server binds on setup and the camera negotiates through HA's managed go2rtc.
* Payload-type numbering is safe: the camera echoes whatever payload type the offer used (99 for
  aiortc, 96 for go2rtc) rather than forcing its own.
* Authorization: a missing or wrong token and an unknown camera id are all refused with 403 before
  any Tuya call is made.

### Not verified, and honest about it

* The corrected session hygiene (disconnect-on-abandonment, circuit breaker, snapshot cache) is
  covered by unit tests; its field verification is a later step, spelled out at the end of the
  session-hygiene plan.
* The 3–5 slot figure is `max_client_num` from TuyaOS IPC firmware documentation, not a measurement
  on this SCD953. Per-slot reclaim time is likewise the documented ~20-minute zombie timer; the
  field trial only brackets it (~10 minutes of retrying from churn-stop to first answer, vendor app
  locked out throughout).

## Risks and open questions

- **R1 — SDP shape. Retired.** Confirmed real (empty video section on a video-first offer) and
  fixed: reorder to audio-first, strip extmap, drop the backchannel m-line outbound, re-insert it as
  a rejected section (with rtpmap) inbound. ~90 lines, in `tools/webrtc-shim/sdp.py`.
- **R2 — HEVC.** The datachannel/fmp4 path (`bridge.go:340-400`) has no equivalent in go2rtc's
  generic `webrtc:` source. Avent models stream H.264 (`README.md:17`), so this is a documented
  non-goal for the builtin backend; option B would restore it.
- **R3 — no ICE servers on the go2rtc leg.** HA clears `ice_servers` and the ws source ignores
  `#ice_servers`. Same-LAN is unaffected (the camera's host candidate is the one that wins, exactly
  as today, including from inside a bridged Docker network where our container's own candidates are
  already unreachable). HA-remote-from-camera setups would regress; document it.
- **R4 — endpoint reachability/auth.** Bind the shim to `127.0.0.1` for go2rtc and a configurable
  LAN bind only when the player page is enabled; carry a per-entry secret in the URL. Deliberately
  *not* on HA's 8123, to stay out of the way of HA's SSL config.
- **R5 — session limits.** Each viewer path (go2rtc producer, player page) is one Tuya session.
  go2rtc fans out to N HA viewers from one session; the player page adds one per tablet. **Answered
  by the first field trial:** the ceiling is `max_client_num`, 3–5 concurrent sessions per Tuya's
  TuyaOS IPC firmware docs (vendor documentation, not measured on this unit), and a full pool
  closes the newcomer. See "First field trial".
- **R6 — talkback side effects.** Issue #72 (DPS 253 stops the lullaby) still applies; keep the
  `sendrecv` audio opt-in even though go2rtc offers a backchannel m-line by default.
- **R7 — HA Core (venv) users** get no managed go2rtc. The player page still works for them; the
  camera entity needs `go2rtc: url:`.
- **R8 — session teardown. Closed (2026-08-09), after its first resolution was refuted.** The
  first live attempt in Home Assistant timed out with "did not answer within 20s" while the camera
  answered a separate probe 90 seconds later in 87 ms — an exhausted session pool, correctly read.
  What this entry originally got wrong was everything after that: it blamed "sessions abandoned by
  an afternoon of testing", claimed normal operation was far better behaved ("one consumer, and
  every dial frees the session before it"), and left teardown resting on the camera reclaiming its
  own slot promptly. The trial logs refuted all three: the churn *was* normal operation — HA's 10 s
  thumbnail poll, a complete Tuya session per poll, ~360/hour — and reclaim of an abandoned slot is
  on ~20-minute zombie timers, far too slow to lean on. Abandoned sessions are now explicitly
  disconnected (own session id only) and unanswered cameras get a 25 s cooldown. See "First field
  trial" and the session-hygiene plan.
- **Open:** the stream comes out at **720p**, not the 1080p the README advertises. Neither the offer's
  `stream_type` (0 vs the skill's 2) nor the `resolution` protocol-312 message moved it; the camera
  acks the resolution command and keeps sending the sub-stream. Worth checking whether the existing
  add-on actually delivers 1080p today — this may be a long-standing behaviour rather than anything
  the new path introduces.
- **Answered:** HA's `preload_stream` camera pref does not keep a Tuya session open — it starts an
  HLS/ffmpeg pipeline on `stream_source()`, which cannot open this backend's `webrtc:ws://` URL and
  only logs "Protocol not found", forever. Discourage it in the docs; a permanently hot stream is
  what the integration's own `keep_stream_running` option is for, which drives go2rtc's preload
  instead (see "What shipped").
